# 파일럿 10건 수기 정규화 작업 안내 (v0.1)

> 지원각(정부지원사업 신청 자격 판정 서비스) / 근거 it(2팀)
> 상태: **작업 시작 전 준비 완료.** 라벨은 아직 한 건도 없다. 시간·합격선은 모두 가정이며 파일럿 뒤에 고친다.
> 정본 규칙: [GOLDSET_라벨링_가이드_v0.1.md](GOLDSET_라벨링_가이드_v0.1.md). 이 문서는 파일럿을 **어떻게 돌리는지**만 적는다.

## 1. 목적

이 10건은 최종 정답셋이 아니라 **시험 운전(파일럿)** 이다. 확인할 것은 세 가지다.

| # | 확인할 것 | 어떻게 아는가 |
|---|---|---|
| 1 | 가이드대로 쓰면 두 사람이 같은 결과를 내는가 | 두 검수자 일치율(요건 F1, 조건 일치, 논리·플래그 일치, 판정 κ) |
| 2 | 3값 판정 규칙이 사람의 판단과 맞는가 | 규칙 평가기 결과와 사람이 쓴 판정(라벨 B) 비교 |
| 3 | 공고 한 건에 시간이 얼마나 드는가 | 라벨 파일의 `time_minutes` (PRIMARY 20건 일정 산정 근거) |

결과가 나쁘면 가이드를 고쳐 **파일럿을 다시** 한다. 정답셋 본작업(PRIMARY 20건)으로 넘어가지 않는다.

## 3. 역할

팀원은 **3명**(백관민·송진명·오현탁)이라 세 역할을 3명이 나눠 맡는다. 라벨러 두 명이 독립이어야 하므로 라벨러는 서로 다른 사람이고, 배정자·점검 담당은 라벨을 쓰지 않는 세 번째 사람이 맡는 편이 가장 깨끗하다.

| 역할 | 하는 일 | 제안(팀 확정 필요) |
|---|---|---|
| 검수자 2명(라벨러 A·B) | 각자 10건의 라벨 A와 라벨 B를 서로 보지 않고 작성 | 백관민, 송진명 |
| 프로필 배정자 1명 | 공고마다 프로필 5개를 정해 배정표에 기록, 추가 프로필 작성 | 오현탁(라벨을 쓰지 않으므로 프로필을 미리 알아도 라벨이 오염되지 않는다) |
| 점검 담당 1명 | 도구 실행, 일치율·규칙 검증 결과 정리, 합의 회의 진행 | 오현탁(배정자와 같은 사람) |

오현탁은 WBS 계획 일수가 가장 많아 라벨 작성(약 6~11시간)을 맡기지 않는 대신 배정·점검을 맡는다. 배정자가 라벨러를 겸해야 하는 경우에는 배정 뒤 자신의 라벨 A를 쓰기 전에 프로필을 보지 않는다고 약속한다.

## 4. 순서

1. **합격선 정하기(결과를 보기 전).** 가이드 §5 표의 `[ ]`를 팀이 채운다. 이 문서의 §8에 제안값을 적어 두었다. 정한 뒤에는 바꾸지 않는다.
2. **프로필 배정.** 배정자가 공고별로 가이드 §4.3 규칙(맞을 것 같음 1+, 아닐 것 같음 1+, 경계값 1, 미입력 1, 나머지 공통)으로 5개를 정해 `profiles_assignment.csv`에 쓴다. 경계값·미입력 프로필은 `profiles_extra.json`에 추가한다.
3. **라벨 A 작성(각자).** 패킷을 읽고 `data/goldset/labels/<검수자>/A/<공고>.json`에 쓴다. 서식은 `templates/`를 복사한다. `labels/<검수자>/`의 `<검수자>`는 영문 짧은 이름으로 정한다(예: `rev1`, `rev2`).
4. **라벨 B 작성(각자).** 라벨 A를 열지 않고 공고 원문으로 배정된 프로필 5개를 판정한다. 끝나면 `cond_ref`만 자신의 라벨 A의 `cond_id`로 채운다.
5. **형식 점검(각자).** `python tools/goldset_check.py validate`로 오류를 고친다.
6. **일치율과 규칙 검증(점검 담당).** `agree`, `rules`를 돌린다.
7. **합의 회의.** 불일치를 원문을 같이 보며 정리해 `data/goldset/adjudication.csv`에 남긴다(§7). 가이드 v0.2에 반영할 항목을 모은다.

### 4-1. 웹 도우미로 쓰기 (JSON을 직접 고치지 않아도 된다)

JSON 서식을 손으로 채우는 대신 **`tools/labeler/labeler.html`** 을 브라우저(Chrome·Edge)로 열어 쓴다. 인터넷 연결이 필요 없고, 입력한 내용은 이 컴퓨터 밖으로 나가지 않는다(자료 패킷이 첨부 원문에서 나온 것이라 일부러 오프라인으로 만들었다).

| 순서 | 할 일 |
|---|---|
| 1 | `labeler.html`을 더블클릭해 연다(① 시작하기 탭). 위쪽에 **이름(영문 짧게, 예: `rev1`)** 을 적는다 |
| 2 | `data/goldset/pilot` 폴더를 **끌어다 놓거나 [폴더 열기]** 를 누른다(패킷 `packets/*.txt`, `profiles*.json`, 배정표 `*.csv`를 알아서 찾는다). 공고 10건이 목록에 뜬다 |
| 3 | **② 요건 쓰기(라벨 A)** 탭: 왼쪽에 **원문**, 오른쪽에 **입력 카드**가 나온다. 원문에서 문장을 **드래그**하면 [근거로 쓰기] 버튼이 떠서 문장을 글자 그대로 복사해 준다(요약·수정 방지) |
| 4 | 요건 카드 → 조건 순으로 채운다. 칸마다 설명이 붙어 있고, "7년 이내"처럼 적고 [적용]을 누르면 연산자·숫자를 채워 주는 도우미도 있다 |
| 5 | 라벨 A를 끝내면 **다른 날** **③ 판정 쓰기(라벨 B)** 탭에서 프로필 5개를 판정한다(§10 #4). 5개는 [배정표대로 선택]으로 고른다 |
| 6 | **④ 점검·내려받기** 탭에서 빨간 오류를 고친다(`validate`와 같은 규칙). [전체를 ZIP으로 내려받기]를 누르면 `labels/<이름>/A·B/공고.json` 구조의 ZIP이 받아진다. 풀어서 `data/goldset/` 안에 넣는다 |
| 7 | `python tools/goldset_check.py validate`로 최종 점검(웹 도우미와 같은 규칙이지만 한 번 더 확인) |

- 작업 내용은 브라우저에 **자동 저장**된다(같은 컴퓨터·같은 브라우저에서만 이어 쓸 수 있다). 브라우저 데이터가 지워지면 사라지므로 파일로도 저장해 둔다.
  - ②·③ 탭 위쪽의 **[이 공고 라벨 A/B 저장(JSON)]** 은 공고 하나를 `<공고>.A.json`·`<공고>.B.json`으로 내려받는다(백업). 옆에 마지막 파일 저장 시각과 "저장 안 된 변경 있음"이 보인다. 제출은 ④ 탭의 ZIP으로 한다.
  - 파일로 저장하지 않은 변경이 **15분** 넘게 있거나 **다른 공고로 넘어가면** 위쪽에 노란 알림이 뜬다. [저장]을 누르거나 [15분 뒤에 다시 알림]을 고른다. 창을 닫을 때도 한 번 묻는다. 연습 공고는 알리지 않는다.
  - 저장한 JSON은 ① 시작하기의 [파일 여러 개 열기]로 다시 연다. ZIP은 바로 열리지 않으므로 풀어서 `labels` 폴더를 끌어다 놓는다. 다른 컴퓨터로 옮길 때도 `pilot` 폴더를 먼저 열고 저장한 JSON을 연다.
- 팀원에게 나눠 줄 때는 패킷·프로필·첨부 원본·도우미·안내서를 한 ZIP으로 묶은 작업 키트(`share/`, git 제외)를 팀 안에서만 전한다.
- 작업 시간(`time_minutes`)은 공고 화면 위쪽의 **[▶ 시간 재기]** 를 눌러 시작하고 **[■ 시간 멈추기]** 로 멈춘다. 자동으로 재지 않으므로 쉴 때는 멈추고, 누르지 않았으면 ④ 탭에서 직접 적는다.
- **연습 공고**: ① 시작하기의 [연습용 예시 공고 만들기]를 누르면 `PRACTICE:구미`가 생긴다. 작성 방법을 보여 주는 예이며 ZIP에는 들어가지 않는다.
- 상대 검수자의 ZIP·라벨은 열지 않는다(§5). 합의 회의 전까지 서로 파일을 주고받지 않는다.
- 도구를 다시 만들 때는 `python tools/make_labeler.py`(템플릿 `labeler.template.html` + 공통 프로필 → `labeler.html`).

## 5. 지켜야 할 것

| 해야 할 것 | 하지 말아야 할 것 |
|---|---|
| 근거 문장(`source_sentence`)은 패킷 원문을 그대로 복사 | 요약하거나 고쳐 쓰기 |
| 원문에 없으면 비워 두고 `ambiguities`에 이유 기록 | "제한 없음"으로 간주해 채우기 |
| 법령·제도 용어는 `needs_definition: true` | 용어의 법적 뜻을 기억으로 적기 |
| 판정이 어려우면 `NEEDS_CHECK`와 `reason_codes` | 억지로 `ELIGIBLE`/`NOT_ELIGIBLE` |
| 모호했던 규칙을 `ambiguities`·메모에 기록(가이드 개정 재료) | 상대 검수자와 라벨을 미리 맞춰 보기 |
| 공고당 걸린 시간을 `time_minutes`에 기록 | 기계 추출 후보(`data/graph/…`)를 열어 보기 |

패킷의 첨부 추출 텍스트는 표·서식이 깨졌을 수 있다. 의심되면 패킷 맨 위의 원본 경로를 열어 확인하되, 근거 문장은 **원본 문서의 문장**을 복사한다. 패킷에 그대로 없는 문장이면 `validate`가 알려 주며, 원본에서 가져온 것이면 정상이다.

개인정보: 공공기관 공고의 담당자 연락처는 라벨에 옮기지 않는다(요건과 무관).


```powershell

```

```powershell

```

| 명령 | 하는 일 | 결과 |
|---|---|---|
| `validate` | 속성·연산자·종류 허용 값, `AT_LEAST`의 `min_count`, 기준일(`ref_date_kind`), `cond_id` 중복, 근거 문장이 패킷에 있는지, 라벨 B의 `cond_ref`·`reason_codes` | 오류 목록 |

| `rules` | 각 검수자의 라벨 A를 규칙 평가기로 평가해 라벨 B와 비교 | `data/goldset/pilot/rules_report.json` |

이 보고서들은 라벨과 같은 성격이라 정답셋 확정 전에는 팀 내부 자료로만 쓴다.

## 7. 불일치를 읽는 법

`rules`에서 규칙 평가기와 사람 판정이 다르면 **정답은 사람 쪽**이다. 다음 중 어느 경우인지 분류해 `adjudication.csv`에 적는다.

| 분류 | 의미 | 조치 |
|---|---|---|
| 규칙 버그 | 평가기가 가이드와 다르게 구현됨 | 평가기 수정, 단위 시험 추가 |
| 가이드 모호 | 가이드가 두 해석을 허용함 | v0.2에서 규칙을 하나로 정함 |
| 라벨 오류 | 검수자가 가이드를 잘못 적용 | 라벨 수정 |
| 데이터 한계 | 원문이 불명확해 판단 불가 | `NEEDS_CHECK`로 기록, 해당 규칙 유지 |

`agree`에서 두 사람이 다른 곳도 같은 방식으로 분류한다. 일치율 숫자보다 **어느 규칙에서 갈렸는가**가 더 중요한 산출물이다.

## 8. 합격선 제안 (팀 결정 필요)

수치는 근거가 있는 값이 아니라 **출발점 제안**이다. 파일럿 표본이 작아(요건 수십 건, 판정 50쌍) 신뢰구간이 넓다는 점을 감안한다.

| 지표 | 제안 합격선 | 이유 |
|---|---|---|
| 요건 F1 | 0.80 이상 | 같은 요건을 같은 구절에서 찾는지. 이보다 낮으면 "요건"의 경계 정의가 모호하다는 신호 |
| 조건 일치(엄격) | 0.70 이상 | 값·연산자까지 같아야 하므로 요건 일치보다 낮게 둔다 |
| 조건 일치(느슨, 속성만) | 0.85 이상 | 속성 선택(어느 필드인가)은 거의 같아야 한다 |
| 논리·플래그 일치 | 0.80 이상 | AND/OR 등 논리와 `open_ended` 판단 |
| 판정 κ | 0.60 이상 | 우연 일치를 뺀 일치도의 일반적 "상당한 일치" 구간 |

판정 κ는 `NEEDS_CHECK`가 많으면 분포가 한쪽으로 쏠려 값이 낮게 나올 수 있다. 쏠림이 크면 일치율(%)과 함께 보고한다.

## 9. 시간 가늠 (가정, 미측정)

| 작업 | 공고당 | 10건 |
|---|---|---|
| 라벨 A | 20~40분 | 3.5~7시간 |
| 라벨 B(프로필 5개) | 15~25분 | 2.5~4시간 |
| 합의 회의 | 5~10분 | 1~1.5시간 |

검수자 1인 기준 약 6~11시간이며 이 값이 PRIMARY 20건 일정 산정의 근거가 되므로 **반드시 실측해 기록한다**(`time_minutes`). 한국어 법령형 문장이 긴 공고가 시간을 크게 좌우한다.

## 11. 한계

- 규칙 평가기가 쓰는 계층은 법령 원문을 확인한 것만이다(소기업·중기업 ⊂ 중소기업). 소상공인·중견 등 정의가 없는 용어는 `UNKNOWN`으로 처리하므로, 사람이 이를 `SATISFIED`/`UNSATISFIED`로 쓰면 어긋나 보인다. 이는 평가기 한계이며 가이드의 `needs_definition` 규칙으로 정리한다.
- 지역 그룹 개념(구 광주광역시, 경상권 등)은 검토 전이라 평가기가 `unreviewed_group` 플래그를 남긴다.
- 파일럿 10건은 K-Startup이 동료가 만든 30건 중에서 뽑혀 모집단 대표성이 없다. 일치율은 **가이드의 품질**을 보는 용도이지 시스템 성능이 아니다.
