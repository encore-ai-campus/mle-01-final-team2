## 1. 결론

**지금까지 측정한 범위에서는 그래프가 SQL보다 낫다는 근거가 없다.** 지역 계층 판정과 정의→법령 경로에서 SQL(폐쇄 테이블, 재귀 CTE)과 그래프(Neo4j)가 기준 구현과 같은 결과를 냈고, 속도는 SQL이 훨씬 빨랐다. 그래프가 필요하다는 주장은 하지 않는다. 계층 **사전**(상위 지역 테이블이나 그래프)은 필요하다는 것만 확인되었다. 그래프가 나은 곳은 정확도·속도가 아니라 **판정 근거를 경로째 돌려주는 설명 출력**이다(E1: 같은 결과를 내는 코드가 강한 SQL보다 토큰 45% 적음, 7절). 법령 개정 영향 찾기(E3)는 SQL과 차이가 거의 없었다. 새 관계·하위 조건을 더하는 스키마 변경(E2)은 3개 중 2개 시나리오에서 그래프 쪽 수정이 적었다. 차이는 거의 다 질의에서 난다(8절).

| 질문 | 답 |
|---|---|
| 정확도(판정 결과)에서 그래프가 낫나 | 아니다. A2·A3·G 모두 기준 구현과 불일치 0건 |
| 속도에서 낫나 | 아니다. 네트워크를 뺀 같은 기기 조건에서도 Neo4j 서버 처리 10ms, 왕복 19ms, SQL 폐쇄 테이블 0.20ms. Aura 왕복 164ms의 대부분(약 156ms)은 네트워크였다(3.2절) |
| 계층 사전이 필요한가 | 필요하다. 계층 없는 SQL 필터(A)는 계층을 올라가야 충족되는 1,883쌍을 하나도 찾지 못했다(재현율 0%) |
| 질의가 더 간단한가 | 조금 간단하다(아래 4절). 다만 SQL도 가능하고 차이는 크지 않다 |
| 판정 근거 설명을 만들기 쉬운가(E1) | 그렇다. 같은 카드를 내는 코드가 강한 SQL 설계보다 토큰 45%·줄 82% 적다(7절). 미리 정한 기준(30% 이상) 달성 |
| 법령 개정 영향 찾기가 쉬운가(E3, CQ-15) | 차이가 거의 없다. 결과는 같고, 깊이를 늘리는 수정은 SQL도 숫자 1개였다. 미리 정한 기준 미달 (7절) |
| 스키마를 바꾸기 쉬운가(E2) | 3개 중 2개에서 그래프 수정이 적다(업종 계층 14 대 6줄, 하위 조건 29 대 13줄, 정정 공고 5 대 5줄). 미리 정한 기준 달성. 차이는 거의 질의에서 난다 (8절) |
| 아직 못 잰 것 | 직접 인용(요건→조문) 경로의 영향 전파, 바꾼 Cypher를 새 구조 위에서 시험하기(E2 한계), 깊은 계층(E4), API 서버에서의 서비스 지연. 5·8·9절 |

### 해석 기준 (결과를 보기 전에 정했다)
1. 구성 X의 판정이 기준 C와 한 쌍도 다르지 않으면 "같은 결과". 다르면 원인을 분해하기 전에는 우열을 주장하지 않는다.
2. 같은 결과이면 그래프의 우위 근거가 아니다. 계층 질의는 SQL(A2·A3)로 풀리므로 그래프 DB가 필요하다는 주장은 하지 않는다.
3. 서버 처리 시간 p50이 A2의 2배 이내면 "비슷", 그보다 크면 "느림", 절반 미만이면 "빠름"으로만 적는다.
4. A의 계층 재현율이 C보다 낮으면 "계층 사전이 필요하다"는 근거로 쓰되 그래프 필요성의 근거로는 쓰지 않는다.
5. 데이터가 없는 질문 유형은 "측정 불가"로 적는다.

같은 기기 구조 판정 베이스라인(`python tools/graphrag/build.py compare`, 모든 구조 조건): 모집 중 공고 1,452건 × 프로필 300개에서 A2와 C 불일치 0. 프로필당 C 34ms, A2 2.3ms(둘 다 같은 프로세스).

### 3.2 시간 (프로필당 질의 묶음, 900회 = 300 프로필 × 3반복)

| 구성 | p50 | p95 | 어디서 도나 |
|---|---:|---:|---|
| A | 0.22ms | 0.28ms | SQLite, 같은 프로세스 메모리 |
| A2 | 0.20ms | 0.26ms | 〃(폐쇄 테이블은 사전에 한 번 만든다) |
| A3 | 0.27ms | 0.33ms | 〃(사전 계산 없이 재귀) |
| C 파이썬 평가기 | 1.12ms | 1.33ms | 같은 프로세스(공고별 조건 객체 평가) |
| G 로컬 Neo4j 서버 처리 | **10ms** | 13ms | 같은 기기 Docker. 서버가 보고한 시간(정수 ms) |
| **G 로컬 Neo4j 왕복** | **19ms** | 24ms | 같은 기기. Bolt·드라이버·직렬화 포함 |
| G Aura 서버 처리 | 9ms | 15ms | 원격 |
| G Aura 왕복 | 164ms | 183ms | 원격. 네트워크 포함 |

빈 질의(`RETURN 1`) 왕복 p50: 로컬 4.5ms, Aura 78ms. G는 지역이 있는 프로필마다 질의를 2번 보내므로 고정 비용이 로컬 약 9ms, Aura 약 156ms다.

**공정성 검토(팀원 지적: "그래프는 원격 Aura라 지연이 있고 SQL은 SQLite라 빨랐을 것").** 맞는 지적이다. 11-25 결과의 왕복 171ms는 거의 전부 네트워크였다(이번 Aura 측정에서 164ms 중 156ms가 빈 질의 왕복 2회). 그래서 같은 그래프를 같은 기기 로컬 Neo4j에 적재해 다시 쟀다.

| 비교 | Neo4j | A2 | 배수 |
|---|---:|---:|---:|
| Aura 왕복(11-25 문서가 보인 격차) | 164ms | 0.20ms | 약 820배 |
| 같은 기기 왕복 | 19ms | 0.20ms | 약 95배 |
| 서버 처리(네트워크 없음, Aura·로컬 비슷) | 9~10ms | 0.20ms | 약 50배 |

- 해석 기준 3은 처음부터 왕복이 아니라 **서버 처리 시간**으로 판단하게 되어 있었고, 서버 시간은 원격(9ms)과 로컬(10ms)이 거의 같다. 따라서 "느림" 판정은 네트워크 때문이 아니며 그대로다. 왕복 시간으로 격차를 말하면 네트워크가 격차를 약 8배 부풀린다.
- 남은 불공정: SQLite는 프로세스 안에 들어 있는(임베디드) DB라 Neo4j 같은 서버형 DB가 내는 질의 접수·계획·직렬화 비용이 없다. 서버형 SQL(PostgreSQL, 팀 저장소로는 Supabase)과의 비교는 아직 재지 않았다. 서버형 SQL도 질의마다 왕복 비용이 붙으므로 왕복 기준 격차는 더 줄 것으로 보이지만, 측정 전이라 수치로 주장하지 않는다.
- G는 충족·미확인을 질의 2번으로 나눴고 SQL은 `UNION` 한 번이다. 질의를 하나로 합치면 고정 비용 한 번(로컬 약 4.5ms)을 줄일 수 있다.
- 이 규모(공고 158건, 간선 319개)에서는 로컬 19ms도 사용자가 느낄 지연이 아니다. 서비스 지연을 정할 때는 FastAPI(AWS)와 Aura 사이의 실제 왕복을 따로 재야 한다.

## 4. 질의 복잡도

| 구성 | 지역 계층 질의 | 사전 준비 |
|---|---|---|
| A2 | 조인 1개(충족)와 조인 1개(미확인) 후 합치기, 약 2줄 | 폐쇄 테이블을 코드로 계산해 적재해야 한다. 간선이 바뀌면 다시 계산 |

그래프 질의가 약간 짧고 사전 계산이 필요 없지만, A3(재귀 CTE)도 폐쇄 테이블 없이 같은 결과를 낸다. 질의가 짧다는 것은 장점이 될 수 있어도 정확도나 속도의 장점은 아니다.

## 4.1 한계 (이 결과를 과하게 읽지 않기 위해)

- **계층이 얕다.** 지역 조건의 대상은 거의 시도·권역이고, 사용자가 시군구·일반구여도 2~3 hop이다. 미확인(조건 지역이 사용자 지역보다 하위) 경로는 이 데이터에서 한 쌍도 나오지 않아 측정에서 시험되지 않았다(단위 시험으로만 확인).
- **규모가 작다.** 지역 조건 공고 158건(11-25 1,122건), 간선 319개. 훨씬 큰 그래프에서는 결과가 달라질 수 있다.
- 일치는 "두 구현이 같다"는 뜻이지 규칙이 옳다는 뜻이 아니다. 정답 라벨이 0건이라 정확도는 재지 못했다.
- Neo4j의 서버 시간은 정수 ms로 보고되어 해상도가 거칠다. Aura 왕복에는 네트워크·공유 부하가 섞이므로 지연 비교는 같은 기기 로컬 측정(3.2절)을 본다.
- SQLite는 임베디드 DB다. 서버형 SQL(PostgreSQL)과의 같은 기기 비교는 아직 하지 않았다.
- SQL은 우리가 짠 것이다. 더 강한 SQL이 있을 수 있어 팀의 검토가 필요하다(공정성).
- 벡터 RAG(B)는 구현하지 않았다.

## 6. 설계서와 KPI에 미치는 영향

- 설계서 7절의 결론("그래프가 SQL보다 필요하다고 말할 수 없다")은 그대로 유지한다. 이번 측정은 이를 **그래프 DB에서도 확인**한 것이다.
- KPI N-07(GraphRAG 대 SQL)은 "우위 목표를 두지 않고 유형별 결과와 지는 유형을 보고한다"는 원칙대로, 이번 결과는 `hierarchy`·`definition` 유형에서 "차이 없음, 속도는 SQL이 빠름(같은 기기 서버 처리 약 50배, 왕복 약 95배)"으로 보고한다.
- 온톨로지의 정당화는 저장소 선택이 아니라 **조건 트리·3값 판정·근거 경로를 한 모델로 합의하고 설명하는 것**에 둔다. 그래프 DB 적재 범위를 줄이고 개념 사전과 조건 트리 모델은 유지하라는 설계서 7절의 해석표 두 번째 행("C와 A2가 모든 유형에서 같다")에 해당한다.
- 다음 측정 우선순위: ① API 서버(AWS)에서 서비스 지연(9절), ② 본문 요건 적재 후 직접 인용 경로의 영향 전파, ③ 깊은 계층(E4). 스키마 변경 비용(E2)은 8절에서 쟀다.

## 7. 근거 경로 설명(E1)과 법령 개정 영향(E3) (2026-11-27 추가)

> 코드: `tools/graphrag/compare_path_impact.py` · 시험: `tools/test_compare_path_impact.py` · 원자료: `data/eval/compare_path_impact.json`
> 가설과 성공 기준은 실험 전에 스키마 정의서 §6.3에 적어 두었다. 같은 그래프 파일로 SQL 테이블을 만들고 Cypher는 Aura(읽기 전용, 저장소 빌드와 같음)에 물었다.

SQL은 두 가지 설계로 짰다.
- **종류별 테이블:** 그래프 라벨을 그대로 옮겨 조문과 별표 테이블이 따로 있다.
- **통합 조항 테이블:** 조문과 별표를 `provision` 한 테이블에 모으고, 표시 이름은 적재할 때 만든다. SQL에 유리한 강한 설계다.

### 7.1 E1 판정 근거 카드

입력은 모집 중 공고 98건이다. 지역 조건이나 정의가 달린 개념 조건이 있는 공고를 골랐고, 공고마다 사용자 지역을 무작위로 붙였다. 출력은 조건·개념마다 다음 세 가지를 담은 카드다.
- 사용자 지역에서 조건 지역까지의 경로
- 개념의 상위 개념(최대 2단계)을 거쳐 닿는 정의
- 그 정의가 인용한 법령의 조문·별표

카드 행은 643개다. 지역 경로가 있는 행이 56개, 법령 근거가 있는 행이 120개다.

| 구성 | 질의 줄 | 후처리 줄 | 합계 | 토큰 | 결과 불일치 |
|---|---:|---:|---:|---:|---:|
| SQL 종류별 테이블 | 38 | 8 | 46 | 433 | 0 / 98 |
| SQL 통합 조항 테이블 | 31 | 8 | 39 | 342 | 0 / 98 |
| Cypher | 5 | 2 | 7 | 189 | 0 / 98 |

- 강한 SQL 설계와 비교해도 Cypher가 토큰 45%, 줄 82% 적다. 미리 정한 기준(결과 일치 + 코드 30% 이상 적음)을 **달성**했다.
- 줄 수는 Cypher 줄이 길어서 차이가 과장된다. 기준 판단은 토큰으로 했다.
- 차이가 나는 곳은 두 군데다.
  - 경로: Cypher는 `nodes(p)`로 경로를 그대로 돌려준다. SQL은 경로 문자열을 쌓는 재귀 CTE가 필요하다.
  - 근거 모으기: Cypher는 `collect()`로 조건마다 근거를 DB 안에서 모은다. SQL은 경로 × 근거로 펼쳐진 행을 파이썬에서 다시 묶는다.

### 7.2 E3 법령 개정 영향 (CQ-15, 정의 경유 경로)

조문이나 별표 하나가 바뀌었다고 가정하고, 그 조항을 인용한 정의에서 출발해 영향받는 공고를 찾는다. 경로는 정의 → 개념 ← 하위 개념 ← 조건 ← 요건 ← 공고다.

| 시나리오 | 입력 | 결과 불일치(종류별·통합 SQL) | 바꾼 줄(더함/뺌): SQL 종류별 · SQL 통합 · Cypher |
|---|---:|---|---|
| S0 조문만, `IS_A` ≤2 | 조문 18개 | 0 · 0 | (기준) |
| S1 별표까지 | 조항 21개 | 0 · 0 | +4/−0 · +0/−0 · +2/−1 |
| S2 `IS_A` ≤3 | 조항 21개 | 0 · 0 | +1/−1 · +1/−1 · +1/−1 |

- 결과는 모두 같다.
- **깊이를 늘리는 수정은 SQL도 숫자 하나였다.** 재귀 CTE의 `hops < 2`를 `< 3`으로 바꾸면 된다. 그래서 미리 정한 기준("Cypher는 숫자 1개, SQL은 CTE 수정")은 **미달**이다. 깊이 변경에서는 차이가 없다.
- 별표를 추가할 때:
  - 종류별 테이블 SQL은 시작점을 합치는 4줄이 늘었다. Cypher는 라벨 하나와 조건 한 줄을 고쳤다.
  - 통합 조항 테이블 SQL은 질의를 고칠 필요가 없다. 그 비용은 테이블을 설계할 때 미리 냈다.
- 실제 영향: 21개 조항 중 모집 중 공고에 닿는 것은 3개다.
  - 「중소기업창업 지원법」 제2조(중장년창업기업 정의): 49건
  - 「1인 창조기업 육성에 관한 법률」 제2조: 132건
  - 같은 법 시행령 별표(제외 업종): 132건

### 7.3 해석과 한계

- 그래프가 나은 점은 **판정 근거를 경로째 돌려주는 설명 출력(E1)**이다. 이것은 화면의 판정 카드(`trace_path`)가 실제로 하는 일이다.
- 법령 개정 영향(E3)은 SQL과 차이가 거의 없다. 정의를 거치는 경로가 고정되어 있고, 깊이는 SQL 재귀에서도 숫자 하나다.
- 한계는 다음과 같다.
  - 하위 개념 관계(`IS_A`)가 2개뿐이라 S2 결과가 S1과 같다. 깊이를 늘려 봐야 실제로는 시험되지 않았다.
  - 요건이 조문을 직접 인용하는 경로(`CITES`)는 아직 없다.
  - 코드량은 우리가 짠 질의 기준이다. 더 짧은 SQL이 있을 수 있어 팀 검토가 필요하다.

## 8. 스키마 변경 비용(E2) (2026-11-27 추가)

> 코드: `tools/graphrag/compare_schema_change.py` · 시험: `tools/test_compare_schema_change.py` · 원자료: `data/eval/compare_schema_change.json`
> 가설과 성공 기준("시나리오 3개 중 2개 이상에서 그래프 수정량이 적다")은 실험 전에 스키마 정의서 §10.3에 적어 두었다.

세 시나리오에서 바꿔야 하는 줄을 셌다. 기준선은 4.2절의 정규화 SQL 스키마와 Q0~Q4다. 수정 줄은 더한 줄과 뺀 줄의 합이다(한 줄을 고치면 2).

| 산출물 | SQL | 그래프 |
|---|---|---|
| 스키마 | DDL(테이블·인덱스) | 유일 제약(`schema.cypher`) |
| 적재 | 원천 → 테이블 대응(테이블당 한 줄) | 적재 검증표(`sync_graph_neo4j.py`의 `SIGNATURE`·`SCOPES`, 관계당 한 줄). 적재 문장 자체는 관계 종류와 상관없이 같다 |
| 질의 | Q0~Q4 수정, 새 질의는 줄 전체 | 같음 |

원천에서 노드·간선 파일을 만드는 추출 코드는 두 쪽이 같아서 세지 않았다.

| 시나리오 | SQL 스키마 | SQL 적재 | SQL 질의 | **SQL 합계**(파일) | 그래프 적재 | 그래프 질의 | **그래프 합계**(파일) | 그래프가 적은가 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| S1 업종 계층(`SUBCLASS_OF`) + 업종 조건 검색(새 질의 Q5) | 0 | +1/−1 | +12 | **14**(2) | +2/−1 | +3 | **6**(2) | 예 |
| S2 하위 조건(`HAS_CHILD`, 3단) | +2/−1 | +1/−1 | +49/−9 | **63**(3) | +2/−1 | +5/−5 | **13**(2) | 예 |
| S2, SQL 트리를 뷰 하나로 | +11/−1 | +1/−1 | +10/−5 | **29**(3) | | | | 예(13 < 29) |
| S3 정정 공고(`SUPERSEDES`) | +2 | +1 | +2 | **5**(3) | +2/−1 | +2 | **5**(2) | 아니다(같음) |

그래프 쪽 스키마(유일 제약)는 세 시나리오 모두 바뀌지 않았다. 새 레이블이 없기 때문이다.

- 그래프가 적은 시나리오는 3개 중 2개(S1, S2)다. 미리 정한 기준을 **달성**했다. S3는 같다.
- 차이는 거의 다 **질의**에서 난다. 스키마와 적재만 보면 차이가 작다.
  - S1: SQL 2줄, 그래프 3줄
  - S2: SQL 5줄(뷰를 쓰면 14줄), 그래프 3줄
  - S3: 둘 다 3줄
- S2에서 차이가 가장 크다.
  - 그래프는 조건을 지나는 질의 5개에 `-[:HAS_CHILD*0..3]->` 한 마디씩만 넣으면 된다.
  - SQL은 질의마다 조건 트리를 펼치는 재귀 CTE가 필요하다. 뷰 하나로 모아도 질의마다 조인 줄을 고쳐야 한다.
- S1의 차이는 새 질의 하나의 길이 차이다(SQL 12줄, Cypher 3줄). 계층 간선을 `concept_edge` 한 테이블에 두는 강한 SQL 설계에서는 테이블을 새로 만들 필요가 없다.
- S3에서는 대신된 공고를 빼는 조건이 두 언어 모두 한 줄씩이다. SQL은 테이블 하나와 인덱스 하나를 더 만들고, 그래프는 검증표 두 줄을 고친다.

**정확성 확인**
- **합성 자료(SQLite):** 바꾼 SQL 질의(뷰 설계 포함)가 새 구조에서 기대한 답을 모두 냈다. 바꾸기 전 질의는 다음을 틀렸다.
  - S2: 그룹 조건 아래의 서울 조건을 놓쳤다.
  - S3: 대신된 공고를 그대로 남겼다.
- **실제 자료(Aura, 읽기 전용):** 새 구조가 아직 없는 지금 자료에서 뒤로 호환을 확인했다. 입력은 S1 2개, S2 69개, S3 31개다.
  - 바꾼 질의가 바꾸기 전 질의와 같은 답을 냈다(차이 0).
  - SQL과 Cypher의 답도 같았다(차이 0).
  - 같은 검사를 SQL은 Aura에서 내려받은 SQLite에서 했다.

**한계**
- 바꾼 Cypher가 **새 구조 위에서** 맞는지는 아직 시험하지 못했다. 쓰기가 필요하기 때문이다. 공유 Aura에는 쓰지 않으며, 로컬 Neo4j에서 할 일로 남긴다.
- 그래프에는 테이블 정의가 없어서, 스키마 변경 비용이 **검증표와 점검 질의로 옮겨 간다.** 예를 들어 `HAS_CHILD` 3단 초과를 막는 점검(V6)이 이미 있다. SQL은 외래 키로 끝점 종류를 보장하지만, 3단 제한은 SQL도 따로 점검해야 한다. 이번 집계에는 두 쪽 모두 점검 질의를 넣지 않았다.
- S2에서 SQL이 모든 하위 조건에 `req_id`를 같이 저장하면(비정규화) 질의 수정은 0줄이 된다. 그래프도 요건에서 모든 조건으로 간선을 두면 0줄이다. 그 대신 두 쪽 모두 트리가 일관된지 지키는 비용이 생긴다. 그래서 두 쪽 모두 정규화 설계로 비교했다.
- 줄 수는 우리가 짠 코드 기준이다. 시나리오 정의와 함께 팀 검토가 필요하다.

## 9. 서비스 경로의 그래프 지연과 판정 근거 카드 (2026-11-27 추가)

> 코드: `tools/measure_service_latency.py` · 시험: `tools/test_measure_service_latency.py` · 원자료: `data/eval/service_latency_local-pc_20261127.json`

E1의 판정 근거 카드를 실제 서비스 코드에 넣었다.
- `api/repositories/graph.py`의 `evidence()`가 질의 한 번으로 카드를 돌려준다. 카드에는 지역 경로, 정의, 조문·별표가 들어 있다.
- 에이전트의 `trace_path`가 이 카드를 받고, `fetch_definition`은 카드의 정의 행을 그대로 쓴다. 그래서 채팅 요청 하나의 그래프 질의가 2번에서 1번이 된다.
- 카드를 못 받으면 예전처럼 두 번 묻는다. 그래프 DB에 닿지 않으면 평가기 경로로 표시한다.
- 같이 고친 것:
  - 정의 질의가 조문(`LawArticle`)만 보고 **별표(`LawAppendix`) 근거를 빠뜨리던 문제**를 고쳤다. 별표는 `[별표 1]`처럼 표시한다.
  - 후보 검색의 지역 질의 3번(전국·충족·미확인)을 1번으로 합쳤다.

측정 방법은 다음과 같다.
- 규칙 엔진으로 무작위 프로필 100개(시드 고정)의 상위 5건을 뽑아 실제 요청과 같은 입력을 만들었다.
- 같은 입력으로 예전 방식과 새 방식을 번갈아 쟀다. 워밍업 5회는 뺐다.
- 측정 위치는 개발 PC → Aura다.

| 무엇 | 예전 | 새 방식 | 결과 불일치 |
|---|---|---|---:|
| 판정 근거(경로 + 정의) | 질의 2번 p50 160ms · p95 409ms | 카드 1번 p50 156ms · p95 333ms | 0 / 105 |

- 후보 검색 지역 질의를 합친 효과가 크다. p50 기준 약 390ms가 줄었다. 질의가 가벼워서 시간이 거의 왕복 횟수로 정해지기 때문이다.
- 근거 카드는 p50이 거의 같고, p95만 약 75ms 줄었다. 카드 질의가 서버에서 하는 일이 많아서(경로 + 정의 + 조항을 한 번에) 왕복 한 번 아낀 만큼이 서버 처리로 상쇄된다.
  - 그래서 카드의 이점은 지연보다 **별표 근거가 빠지지 않는 것과 코드가 한 곳에 모인 것**이다.
