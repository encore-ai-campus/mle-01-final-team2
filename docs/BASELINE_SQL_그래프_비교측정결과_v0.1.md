## 1. 결론

**지금까지 측정한 범위에서는 그래프가 SQL보다 낫다는 근거가 없다.** 지역 계층 판정과 정의→법령 경로에서 SQL(폐쇄 테이블, 재귀 CTE)과 그래프(Neo4j)가 기준 구현과 같은 결과를 냈고, 속도는 SQL이 훨씬 빨랐다. 그래프가 필요하다는 주장은 하지 않는다. 계층 **사전**(상위 지역 테이블이나 그래프)은 필요하다는 것만 확인되었다.

| 질문 | 답 |
|---|---|
| 정확도(판정 결과)에서 그래프가 낫나 | 아니다. A2·A3·G 모두 기준 구현과 불일치 0건 |
| 속도에서 낫나 | 아니다. 서버 처리 시간 중앙값 Neo4j 9.0ms, SQL 폐쇄 테이블 0.37ms(약 24배 느림) |
| 계층 사전이 필요한가 | 필요하다. 계층 없는 SQL 필터(A)는 계층을 올라가야 충족되는 24,759쌍을 하나도 찾지 못했다(재현율 0%) |
| 질의가 더 간단한가 | 조금 간단하다(아래 4절). 다만 SQL도 가능하고 차이는 크지 않다 |
| 아직 못 잰 것 | 정의 변경 전파(CQ-15), 경로 설명 생성 비용, 변경 비용, 깊은 계층. 5절 |

## 2. 측정 설정

| 항목 | 값 |
|---|---|
| 스냅샷 | 그래프 파일 노드 31,506·간선 55,903(적재한 것과 같은 파일), 정리층 `data/cleaned/20261124` |
| 대상 | 모집 중이고 지역 조건이 있는 공고 1,122건 × 가상 프로필 300개(시드 20261124, 지역은 시도·시군구·일반구 중 무작위) = 336,600쌍 |
| 판정 | 지역 조건 3값: 충족(사용자 지역이 조건 지역 또는 그 하위, 최대 3 hop), 미확인(조건 지역이 사용자 지역보다 하위), 불충족(그 외) |
| 반복 | 프로필당 3회, 워밍업 5프로필 제외, 같은 기기. 시간은 프로필 하나에 대한 질의 묶음(충족 질의 + 미확인 질의) |

| 구성 | 설명 |
|---|---|
| **A** SQL 필터 | 사용자 지역과 조건 지역이 같은 값일 때만 충족. 계층 없음 |
| **A2** SQL + 폐쇄 테이블 | 사전에 계산한 (지역, 상위 지역, hop) 테이블을 조인 |
| **A3** SQL 재귀 CTE | 질의 시점에 `WITHIN`·`MEMBER_OF` 간선을 재귀로 따라감(폐쇄 테이블 없음) |
| **C** 파이썬 평가기 | 기준 구현(`evaluator.evaluate_condition`) |
| **G** Neo4j(Cypher) | 적재한 그래프에서 `[:WITHIN\|MEMBER_OF*0..3]` 경로 질의 |

공정성: 모든 구성이 같은 공고 집합·같은 코드표와 묶음 사전·같은 3값 규칙·같은 hop 한도(3)를 쓴다. A2·A3는 그래프와 같은 간선 파일에서 테이블을 만들었다.

### 해석 기준 (결과를 보기 전에 정했다)
1. 구성 X의 판정이 기준 C와 한 쌍도 다르지 않으면 "같은 결과". 다르면 원인을 분해하기 전에는 우열을 주장하지 않는다.
2. 같은 결과이면 그래프의 우위 근거가 아니다. 계층 질의는 SQL(A2·A3)로 풀리므로 그래프 DB가 필요하다는 주장은 하지 않는다.
3. 서버 처리 시간 p50이 A2의 2배 이내면 "비슷", 그보다 크면 "느림", 절반 미만이면 "빠름"으로만 적는다.
4. A의 계층 재현율이 C보다 낮으면 "계층 사전이 필요하다"는 근거로 쓰되 그래프 필요성의 근거로는 쓰지 않는다.
5. 데이터가 없는 질문 유형은 "측정 불가"로 적는다.

## 3. 결과

### 3.1 판정 일치 (유형 `hierarchy`, CQ-01·04·17)

| 구성 | 기준 C와 다른 쌍 | 비고 |
|---|---:|---|
| A2 SQL 폐쇄 테이블 | **0** / 336,600 | |
| A3 SQL 재귀 CTE | **0** / 336,600 | |
| G Neo4j | **0** / 336,600 | |
| A SQL 필터(계층 없음) | 24,759 / 336,600 | 모두 "충족인데 불충족으로 판정". 시군구·일반구 프로필 284개 전부에서 발생, 시도 프로필 16개는 0 |

계층 재현율(N-04, 계층을 1 hop 이상 올라가야 충족되는 쌍): **A 0 / 24,759 = 0%**, A2·A3·G 100%.

### 3.2 시간 (프로필당 질의 묶음, 900회 = 300 프로필 × 3반복)

| 구성 | p50 | p95 | 비고 |
|---|---:|---:|---|
| A | 0.22ms | 0.32ms | |
| A2 | 0.37ms | 0.57ms | 폐쇄 테이블은 사전에 한 번 만든다 |
| A3 | 0.44ms | 0.67ms | 사전 계산 없이 재귀 |
| C 파이썬 평가기 | 4.61ms | 5.20ms | 공고별 조건 객체 평가 포함 |
| **G Neo4j 서버 처리** | **9.0ms** | 13.0ms | 서버가 보고한 시간(정수 ms) |
| G Neo4j 왕복 | 171ms | 241ms | 원격 Aura까지의 네트워크 포함 |

해석 기준 3에 따라 Neo4j는 A2 대비 **"느림"**(약 24배)이다. 단, 이 비교는 공정하지 않은 점이 있다: SQLite는 같은 프로세스의 메모리 안에서 돌고 Neo4j는 원격 서버다. 서버 시간만 보아도 느리고, 왕복까지 더하면 격차가 훨씬 크다. 이 규모(공고 1,122건, 간선 319개)에서는 어느 구성도 사용자가 느낄 지연이 아니다.

### 3.3 정의→법령 경로 (유형 `definition`, CQ-05)

| 구성 | 결과 | 시간 | 질의 |
|---|---|---|---|
| SQL | 4행 | 3.6ms | 조인 5개 |
| Cypher | 같은 4행 | 서버 31ms, 왕복 108ms | 경로 패턴 1개(3 hop) |

결과가 같고(중소기업 → 제2조, 창업기업 → 제2조 …), 건수가 4행뿐이라 시간 비교는 의미가 작다.

## 4. 질의 복잡도

| 구성 | 지역 계층 질의 | 사전 준비 |
|---|---|---|
| A2 | 조인 1개(충족)와 조인 1개(미확인) 후 합치기, 약 2줄 | 폐쇄 테이블을 코드로 계산해 적재해야 한다. 간선이 바뀌면 다시 계산 |
| A3 | 재귀 CTE 2개(위로, 아래로) + 조인, 약 5줄 | 없음(간선 테이블만) |
| G | 경로 패턴 1개씩, 각 2줄: `(u)-[:WITHIN\|MEMBER_OF*0..3]->(t)<-[:ABOUT]-(c)<-...-(n)` | 없음 |

그래프 질의가 약간 짧고 사전 계산이 필요 없지만, A3(재귀 CTE)도 폐쇄 테이블 없이 같은 결과를 낸다. 질의가 짧다는 것은 장점이 될 수 있어도 정확도나 속도의 장점은 아니다.

### 4.2 정규화 스키마 기준 코드량 재측정 (2026-11-26 추가)

위 표의 SQL은 공고→지역 조건을 미리 펼친 `notice_region` 테이블을 써서 조인이 적게 잡혔다. 그래서 그래프를 정규화한 관계형 테이블 11개로 그대로 옮긴 뒤 다시 쟀다. 같은 질문 5개를 두 언어로 짰고, 결과 불일치 0을 확인한 다음 셌다. 계층·다단 질의 4개(Q1~Q4) 합계는 다음과 같다.

| 지표 | SQL | Cypher |
|---|---:|---:|
| 줄 수 | 58 | 13 |
| 토큰 수 | 539 | 300 |
| 재귀 CTE | 4 | 0 |

재귀 없는 단순 조회(Q0)는 차이가 없다(토큰 SQL 32, Cypher 40). 질문별 표와 해석은 `docs/SCHEMA_Neo4j_그래프스키마정의서_v0.1.md` §10.2에 있다. 재현은 `python tools/graphrag/compare_query_size.py`로 한다.

## 4.1 한계 (이 결과를 과하게 읽지 않기 위해)

- **계층이 얕다.** 지역 조건의 대상은 거의 시도·권역이고, 사용자가 시군구·일반구여도 2~3 hop이다. 미확인(조건 지역이 사용자 지역보다 하위) 경로는 이 데이터에서 한 쌍도 나오지 않아 측정에서 시험되지 않았다(단위 시험으로만 확인).
- **규모가 작다.** 공고 1,122건, 간선 319개. 훨씬 큰 그래프에서는 결과가 달라질 수 있다.
- 일치는 "두 구현이 같다"는 뜻이지 규칙이 옳다는 뜻이 아니다. 정답 라벨이 0건이라 정확도는 재지 못했다.
- Neo4j의 서버 시간은 정수 ms로 보고되어 해상도가 거칠다. 원격 서버라 네트워크·부하가 섞인다.
- SQL은 우리가 짠 것이다. 더 강한 SQL이 있을 수 있어 팀의 검토가 필요하다(공정성).
- 벡터 RAG(B)는 구현하지 않았다.

## 5. 측정하지 못한 것 (그래프의 장점이 있다면 여기서 나올 후보)

| 후보 | 측정 불가 이유 | 필요한 것 |
|---|---|---|
| 정의가 바뀌면 영향받는 공고 찾기(CQ-15) | 공고의 법령 인용이 요건 노드에 연결되지 않았다(`CITES` 543건 보류) | 본문 요건 적재 후, 조문 하나를 바꿨을 때 영향 공고 집합을 SQL과 그래프로 비교 |
| 판정 근거 경로를 결과로 직접 반환 | 경로를 문자열로 돌려주는 SQL을 짜서 비교해야 한다 | 같은 설명 출력을 만드는 데 드는 코드·시간 비교 |
| 새 관계·조건 유형을 추가할 때의 변경 비용 | 비교 기준이 아직 없다 | 변경 시나리오 3개 정해 수정 줄 수 측정 |
| 정정·재공고(`SUPERSEDES`) 이력 질의 | 재수집을 하지 않아 버전이 모두 1 | 재수집 후 |
| 깊은 계층·다단 조건 트리 | 현재 데이터가 얕다 | 본문 요건과 일반구 이하 조건이 늘어난 뒤 |

## 6. 설계서와 KPI에 미치는 영향

- 설계서 7절의 결론("그래프가 SQL보다 필요하다고 말할 수 없다")은 그대로 유지한다. 이번 측정은 이를 **그래프 DB에서도 확인**한 것이다.
- KPI N-07(GraphRAG 대 SQL)은 "우위 목표를 두지 않고 유형별 결과와 지는 유형을 보고한다"는 원칙대로, 이번 결과는 `hierarchy`·`definition` 유형에서 "차이 없음, 속도는 SQL이 빠름"으로 보고한다.
- 온톨로지의 정당화는 저장소 선택이 아니라 **조건 트리·3값 판정·근거 경로를 한 모델로 합의하고 설명하는 것**에 둔다. 그래프 DB 적재 범위를 줄이고 개념 사전과 조건 트리 모델은 유지하라는 설계서 7절의 해석표 두 번째 행("C와 A2가 모든 유형에서 같다")에 해당한다.
- 다음 측정 우선순위: ① 본문 요건 적재 후 CQ-15 영향 전파, ② 경로 설명 출력 비교, ③ 변경 비용.
