# SQL 대 그래프 예비 실험 — 1단계 적재 설계와 샘플 질문 초안

*작성일 2026-11-19 · 상태: 초안(팀 합의 전) · 선행 문서: [ONTOLOGY_NECESSITY.md](ONTOLOGY_NECESSITY.md) §5 · 설계 기준: [ONTOLOGY_DESIGN.md](ONTOLOGY_DESIGN.md)*

## 1. 목적과 원칙

"온톨로지·그래프가 SQL보다 나은 질문 유형이 있는가"를 **작은 규모의 사례 비교**로 확인한다. 통계적 결론이 아니라 예비 실험이며, 발표에서도 그렇게 표현한다.

- **같은 입력, 같은 해소 규칙**: 두 저장소 모두 `data/ibk_converted/parsed`와 `data/상위법령_변환/구조화`의 같은 JSON에서 적재하고, 약칭·이름 정규화 규칙도 하나만 쓴다. 한쪽에만 유리한 전처리를 넣지 않는다.
- **SQL을 약하게 만들지 않는다**: SQL 쪽 스키마는 관계를 하나의 유형 컬럼이 있는 간선 테이블로 두고, 필요한 인덱스를 모두 만든다. 유형별 테이블로 나눈 변형도 함께 재서, "새 관계 유형 추가" 비용 비교가 불리한 설계 탓이 되지 않게 한다.
- **1단계는 LLM이 필요 없다**: 결정 층(파서가 만든 구조와 인용 관계)만 적재한다. 의무·직무 같은 추출 층은 5~10건을 **손으로** 만들어 개념 증명만 한다(§6 유형 E·F).
- 질문 정답은 **사람이 원문을 보고 만든다.** 어느 저장소의 출력도 정답으로 쓰지 않는다.

### 2.2 법령 — 적재 단계에서 확정

사규가 인용하는 법령 중 코퍼스(275건)에 있는 문서와 그 시행령·시행규칙(`IMPLEMENTS`, 이름 규칙으로 결정적)을 넣는다. 인용 횟수가 많은 후보는 금융회사의 지배구조에 관한 법률(17), 은행법(10), 청탁금지법(9, 정식명칭 "부정청탁 및 금품등 수수의 금지에 관한 법률"), 부패방지권익위법(9), 도로교통법(6), 금융소비자 보호에 관한 법률(4), 공직자의 이해충돌 방지법(약칭 이해충돌방지법 포함 5)이다. **약칭이 많아 약칭 사전(설계서 §8.2) 없이는 해소가 안 된다.** 파일럿용으로 위 약칭 10~15개를 직접 만든다. 법령 문서와 조문 수는 사전 적용 후 산출한다.

### 2.3 처리 규칙

- 삭제 조문(`deleted=true`)은 노드로 만들되 검색 질의에서는 제외한다(설계서 D8).
- 코퍼스 밖 대상(휴가규정·보수규정·위임전결규정 등 ALIO에 없는 내규)은 `ExternalLaw` 스텁으로 둔다. 질문 유형 G가 이 스텁을 쓴다.
- 별표·서식은 없다(설계서 D11). 별표에 의존하는 질문은 만들지 않는다.
- `unresolved_refs`는 설계서 D1 때문에 `to`를 믿지 않는다. 파일럿에서는 **재해소하지 않고 제외**하고 건수만 보고한다(해소 로직은 동료 담당 범위).

## 3. 공통 논리 스키마와 두 저장소 매핑

설계서 §5~6의 결정 층을 그대로 쓴다. 파일럿에서 쓰는 요소만 추렸다.

| 논리 요소 | Postgres(SQL) | Neo4j(그래프) |
|---|---|---|
| 문서 | `document(doc_id PK, title, source_kind, doc_type, authority_rank, effective_date)` | `(:Document {doc_id UNIQUE, …})` |
| 조문 | `article(article_id PK, doc_id FK, no, title, text, deleted)` | `(:Article {id UNIQUE, …})`, `(:Document)-[:HAS_ARTICLE]->(:Article)` |
| 미보유 스텁 | `ext_law(ext_id PK, norm_name UNIQUE, kind, collect_status)` | `(:ExternalLaw {norm_name UNIQUE})` |
| 조문 간 참조 | 간선 테이블 `edge`의 `rel_type='REFERS_TO'` | `(:Article)-[:REFERS_TO]->(:Article)` |
| 문서 인용 | `edge`의 `rel_type='CITES'` (`to_doc` 또는 `to_ext`) | `(:Article)-[:CITES]->(:Document\|:ExternalLaw)` |
| 위임 | `edge`의 `rel_type='DELEGATES_TO'` | `(:Article)-[:DELEGATES_TO]->(:Document)` |
| 상하위 법령 | `edge`의 `rel_type='IMPLEMENTS'` (문서 간) | `(:Document)-[:IMPLEMENTS]->(:Document)` |

```sql
-- SQL 쪽 간선 테이블(유형 컬럼 방식). 대안으로 유형별 테이블 방식도 만들어 비교한다.
CREATE TABLE edge (
  edge_id    bigserial PRIMARY KEY,
  rel_type   text NOT NULL CHECK (rel_type IN ('REFERS_TO','CITES','DELEGATES_TO','IMPLEMENTS')),
  from_id    text NOT NULL,           -- article_id 또는 doc_id
  to_id      text NOT NULL,           -- article_id, doc_id 또는 ext:<norm_name>
  to_kind    text NOT NULL CHECK (to_kind IN ('article','document','external')),
  cross_doc  boolean,
  resolution text,
  context    text
);
CREATE INDEX edge_from ON edge (from_id, rel_type);
CREATE INDEX edge_to   ON edge (to_id, rel_type);
```

가변 깊이 질의 비교용 예시(질문 C1 형태):

```sql
WITH RECURSIVE walk(article_id, depth, path) AS (
  SELECT 'REPLACE_START', 0, ARRAY['REPLACE_START']
  UNION ALL
  SELECT e.to_id, w.depth + 1, w.path || e.to_id
  FROM walk w JOIN edge e ON e.from_id = w.article_id AND e.rel_type = 'REFERS_TO'
  WHERE w.depth < 3 AND NOT e.to_id = ANY(w.path)      -- 순환 방지
)
SELECT DISTINCT article_id FROM walk WHERE depth > 0;
```

```cypher
MATCH p = (s:Article {id: $start})-[:REFERS_TO*1..3]->(t:Article)
RETURN DISTINCT t.id;
```

이 정도로 단순한 경로 질문은 **두 방식이 비슷하다**고 예상한다. 차이는 관계 유형이 섞이거나 규칙이 붙는 질문에서 나올 수 있는지를 본다.

### 3.1 저장소 선택

- **Postgres**: 로컬 Docker를 권장한다. 팀의 Supabase(시스템 기록용)에 실험 테이블을 섞지 않기 위해서다.
- **Neo4j**: 팀의 Aura 인스턴스를 쓰면 설계서의 정식 적재와 충돌할 수 있으므로, 실험은 별도 데이터베이스나 로컬 Neo4j를 쓰는 편이 안전하다. 어느 쪽을 쓸지는 적재 담당 동료와 정한다.

## 4. 적재 절차

1. **입력 고정**: 파일럿 대상 JSON 목록을 `pilot_manifest`로 확정하고 파일 해시를 기록한다.
2. **중간 표현**: 로더가 JSON을 읽어 문서·조문·간선·스텁을 한 번만 계산한다(약칭 사전·이름 정규화 적용). 이 표현을 두 저장소가 공유한다.
3. **적재**: 중간 표현을 Postgres와 Neo4j에 각각 쓴다. 두 번째 실행에도 결과가 같아야 한다(멱등, `claim_id` 규칙은 설계서 §6.3).
4. **건수 검증**: 문서·조문·유형별 간선 수가 중간 표현과 두 저장소에서 모두 일치하는지 확인한다.
5. **점검 쿼리**: 삭제 조문을 가리키는 참조, 같은 간선 중복, 대상 없는 간선이 0건인지 확인한다(설계서 §14.2).
6. **손으로 만드는 추출 층(유형 E·F용)**: `Role` 10개 내외, `Obligation` 5~10건, `CONFLICTS_WITH` 후보 3~5쌍을 CSV로 직접 작성하고 두 저장소에 같은 방식으로 넣는다. 원문 근거(`evidence_text`)가 없는 건은 넣지 않는다.

예상 작업 규모는 로더와 검증까지 **1~2명이 며칠** 정도로 가늠한다. 근거 없는 추정이므로 담당 동료와 확인이 필요하다.

## 5. 측정과 판정 기준(제안)

| 항목 | 방법 |
|---|---|
| 정답 일치 | 사람이 만든 정답 집합과의 정밀도·재현율. 두 방식의 출력이 같으면 "차이 없음" |
| 질의 작성 분량 | 질의 줄 수, 조인·재귀·서브쿼리 수 |
| 질의 작성 시간 | 한 사람이 처음 작성할 때 걸린 시간(참고용, 개인차 큼) |
| 실행 시간 | 웜업 후 20회의 p50·p95. 규모가 작아 차이가 없을 가능성이 크다 |
| 관계 유형 추가 비용 | 새 관계 유형 1개를 넣을 때 바꿔야 하는 질의·스키마 수(유형 컬럼 방식과 유형별 테이블 방식 모두) |

판정은 **첫 측정 전에** 정한다. 제안안:

- 두 방식 정답이 같고 작성 분량도 비슷하면 그 유형은 **차이 없음**으로 보고한다.
- 정답이 같아도 질의 분량이 2배 이상 차이 나는 유형만 "작성 비용 우위"로 적는다. 정답이 다르면 먼저 입력·규칙 차이를 점검한다.
- 어느 유형에서도 우위가 없으면 그대로 보고하고 온톨로지 필요성 논거를 범위(규칙 추론·직무 계층)로 좁힌다.

| E2 | 계층·상속 | 인사부장에게 적용되는 규정 조문을 모두 찾아라 | `미확인`. `Role` 수작업과 "적용 대상" 문구 추출이 선행 | 계층 조인이 겹침 → **차이 후보**, 단 수작업 데이터 품질에 의존 |
| E3 | 계층·상속 | 임원에게 적용되는 복무 규정과 그 위임전결 규정 인용은? | 임원 복무규정 제5·8·16조가 위임전결규정을 인용 / `확인`, 위임전결규정은 코퍼스 밖이라 스텁 | 비슷함 |
| F1 | 규칙 추론 | 사규 의무 중 같은 대상의 상위 법령 의무보다 기한이 긴(느슨한) 것은? | 쌍은 사람이 3~5개 선정(`미확인`). 별표 의존 항목은 제외(설계서 D11) | 비교 질의를 쌍마다 작성 vs 규칙 1개 → **차이 후보** |
| F2 | 규칙 추론 | `authority_rank`가 다른 의무 쌍 중 수치·허용 여부가 상충하는 후보는? | `미확인` | F1과 같음 |
| G1 | 근거 없음 | 위임전결규정의 결재 한도는? | 근거 없음: `ExternalLaw{사내미공개내규}`로 응답 / `확인`(코퍼스에 문서 없음, ALIO 제목 검색에서 확인) | 동일(스텁 조회) |
| G2 | 경계 | 삭제된 조문을 가리키는 참조가 있는가? | `미확인` | 동일 |

유형별 질문 수: A 4, B 3, C 3, D 2, E 3, F 2, G 2(합 19). 확정 전에 팀이 질문을 더하거나 줄인다.

**솔직히 말해 예상되는 결과**: A·B·C 유형은 SQL과 차이가 없을 가능성이 높다. 그래도 그대로 보고한다. 차이 후보는 D1·E2·F1·F2뿐이며, 이 중 E2·F1·F2는 **수작업으로 만든 소량의 추출 데이터**에 기대므로 "온톨로지로 이런 질의가 가능하다"는 개념 증명이지, 자동 추출이 잘 된다는 증거는 아니다.

## 7. 한계

- 질문 19개, 17개 문서는 통계적 결론을 내기에 작다. 사례 비교로만 해석한다.
- 규모가 작아 실행 시간 차이는 의미가 없을 가능성이 크다.
- 유형 E·F는 수작업 데이터라 자동 추출 품질이 반영되지 않는다.
- 약칭 해소·미해결 참조 재해소는 동료 담당 범위이며, 파일럿은 간소 사전으로 대체한다.
- 정답을 만드는 사람이 한 방식에 익숙하면 작성 분량 비교가 기울 수 있다. 가능하면 SQL 질의와 Cypher 질의를 서로 다른 사람이 쓴다.

## 7.1 용어 풀이

| 표현 | 쉬운 설명 |
|---|---|
| SQL 베이스라인 | 비교의 기준이 되는 SQL 방식. 그래프 방식이 정말 나은지 보려면 SQL도 최선으로 짜 놓고 견줘야 한다. |
| 재귀 CTE | SQL에서 자기 자신을 반복 호출해 연결된 행을 따라가는 쿼리. 가변 깊이 경로는 이것으로 된다. |
| Cypher | Neo4j(그래프 DB)의 질의 언어. `-[:REFERS_TO*1..3]->`처럼 경로 모양을 그대로 쓴다. |
| 해소(resolution) | 본문에 적힌 이름("청탁금지법")을 실제 문서·조문 한 곳에 연결하는 작업. 약칭이 많아 사전이 있어야 된다. |
| 약칭 사전 | 약칭과 정식 명칭의 대응표. 같은 법을 두 저장소가 같은 방식으로 찾게 하는 기준이 된다. |
| `unresolved_refs` | 해소하지 못한 참조 목록. 설계서 D1에 따라 가리키는 대상(`to`)을 믿을 수 없어 파일럿에서는 제외하고 건수만 센다. |
| 간선(edge) | 두 노드를 잇는 선. 조문 A가 조문 B를 참조하면 A→B 간선이 하나 생긴다. |
| 중간 표현 | JSON을 읽어 문서·조문·간선을 한 번만 계산해 둔 결과물. 두 저장소가 같은 것을 받아 가야 입력이 같아진다. |
| 멱등(idempotent) | 같은 적재를 두 번 실행해도 결과가 같은 성질. 중복 행이 생기지 않아야 한다. |
| `pilot_manifest`와 해시 | 파일럿 대상 파일 목록과 각 파일의 지문. 입력이 중간에 바뀌지 않았음을 증명한다. |
| p50·p95 | 같은 질의를 여러 번 돌렸을 때 중간값(p50)과 느린 쪽 5% 경계(p95). 평균보다 안정적으로 속도를 비교한다. |
| 웜업 | 첫 실행은 캐시가 비어 느리므로 몇 번 돌린 뒤에 재는 것. |
| `확인` / `미확인` | 정답을 이미 원문으로 확인했는지 여부. `미확인`은 아직 사람이 확정하지 못한 질문이다. |
| 개념 증명 | 자동으로 잘 된다는 증거가 아니라 "이런 질의가 가능하다"만 보이는 소규모 시연. |
