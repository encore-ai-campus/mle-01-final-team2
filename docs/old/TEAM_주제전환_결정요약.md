# 주제 전환 결정 요약 (팀 공유용, 2026-11-23)

**결정할 것:** 프로젝트 주제를 지금의 사규 준수 검토에서 정부지원사업 공고 자격 판정으로 바꿀지, 유지할지.

## 1. 왜 논의하나

- 멘토링에서 “SQL로도 가능해서 온톨로지가 필요 없다”는 지적을 받았다. 우리 평가도 사규 주제의 온톨로지 필요성은 **약~중**이다(`ONTOLOGY_NECESSITY.md` §3.10).
- 강사님 의견(전해 들은 내용): 공고문의 여러 필요 사항을 **계층으로 나눠 합쳐 검색**하고, 온톨로지가 필요한 기능은 따로 고민한다. 이 방향이 **취업용 포트폴리오에 더 알맞다**.

## 2. 비교

| 관점 | 사규 준수 검토(현재) | 공고 자격 판정(대안) |
|---|---|---|
| 온톨로지 필요성 | 조문 간 인용·위임이 재귀적이라 구조적으로 적합. 정직한 평가는 약~중 | 속성 중심 데이터라 SQL로 풀리는 부분이 더 많음. 정의→법령 연결, 조건 설명, 출처 통합에서 정당화해야 함 |
| 데이터 | ALIO 수동 수집 완료(사규 148종, 법령 275건), 버전 1개 | 공개 API로 매일 갱신 가능. 신규·정정 공고가 계속 생김 |
| 시연·윤리 | 인사 모드 오남용 방지 게이트 부담이 큼 | 조건 입력 시연이 쉽고 윤리 게이트 부담이 작음 |
| 포트폴리오 | 금융·준법 직군에 강한 서사 | 수집·정규화·그래프·평가를 한 서비스로 보이기 쉬움(지원 직군에 따라 다름) |
| 경쟁 | 공개 사례를 확인하지 못함 | 공고 검색·매칭 서비스가 이미 있음(직접 확인 전) |
| 위험 | 일정 안정 | 지금 2주차라 재작업 큼 |

## 3. 사전 확인 결과 (상세: `PRECHECK_공고주제_사전확인.md`)

**확인한 것**
- K-Startup API: 무료, 이용허락 제한 없음, JSON·XML. 업력·연령이 이미 **구간 값**으로 제공되고, 세부 자격과 제외 조건은 서술 필드에 있다.
- 기업마당 API: 인증키 필요. 구조화된 자격 필드는 지원대상 1개뿐이고, 요건은 사업개요 서술과 첨부에 있다.
- **K-Startup은 robots.txt가 공고 목록 HTML과 첨부 경로를 막는다.** API만 써야 한다.
- 기업마당 공고 15건(2026-11-20 등록분)을 읽었다. 법령 조문을 직접 인용한 공고 2건, 법령·제도 이름이 나온 공고 4건, AND가 명시된 공고 2건, 제외 조건이 분리된 공고 1건이다. 기준일은 공고마다 달랐다(공고일·접수 마감일·전년도).
- 첨부 15건 중 13건이 **hwpx**다. 우리 HWP5 파서로는 읽을 수 없어 새 파서가 필요하다.

**확인하지 못한 것**
- 인증키를 발급하지 않아 **실제 API 응답**을 보지 못했다.
- 표본이 작고 치우쳐 있다(비무작위, 한 포털·하루치, 창업 분야 3건). 첨부와 이용약관도 읽지 않았다.

## 4. 사전 확인이 말해 주는 것

- 데이터 확보는 **가능성이 있다.** 막는 요인은 아직 보이지 않는다.
- 그러나 **그래프가 꼭 필요하다는 근거는 늘지 않았다.** 정형 값은 SQL로 충분하고, 그래프가 의미 있는 곳(법령 정의 연결, 기준일·트랙 정규화, 설명)은 표본에서 소수였다.
- 공고 주제도 “SQL로 가능” 지적을 피하지 못한다. 오히려 더 강하게 받을 수 있다. 어느 쪽이든 **SQL 베이스라인과 질문 유형별로 비교해 지는 유형도 보고**해야 한다.
- 주제를 바꾸는 이유가 “온톨로지 필요성”이라면 전환만으로는 해결되지 않는다. 이유가 “데이터 갱신·시연·포트폴리오”라면 전환의 장점이 있다.

## 5. 온톨로지가 필요해질 수 있는 후보 기능 (공고 주제)

어느 기능도 “SQL로 불가능”하다고 주장하지 않는다. 온톨로지의 몫은 **정의 변경의 전파, 분류 체계 정렬, 판정 근거의 경로 설명**으로 한정한다. 근거 강도는 모두 **실험 전 가설**이다(표본 15건 기준, 상세는 대안 초안 §1.2).

| # | 기능 | 하는 일(한 줄) | 근거 강도 | 먼저 확인할 것 |
|---|---|---|---|---|
| 1 | 법정 정의 도출 | 업종·매출·근로자 수로 중소기업·소상공인 등 여부를 법령 기준으로 도출해 여러 공고에 일괄 적용 | 중 | 법령·제도 정의에 의존하는 요건 비율(표본 확대). 법령 내용은 원문 확인 필요 |
| 2 | 분류 체계 정렬·다중 소속 구역 | 공고마다 다른 업종 서술을 정렬하고, 주소를 지정 구역 여러 곳에 소속시킴 | 약~중 | 지정 구역 데이터 확보 여부, 임베딩 검색 대비 이득 |
| 3 | 최소 변경 설명·질문 순서 | “무엇을 바꾸면 가능한가”와 후보를 가장 줄이는 질문 순서 | 약~중 | 조건 트리가 필요한 공고 비율 |
| 4 | 지원사업 사다리·중복 제약 | 선행 수혜가 후속 자격이 되는 관계로 “다음에 받을 수 있는 사업” 추천 | 약~중 | 선행·중복 조건 명시 빈도, 수혜 이력 입력의 개인정보 허용 여부 |
| 5 | 입수 시점 검증·정의 변경 전파 | 정정 공고 요건 diff, 법령 정의 변경 시 영향 공고 탐색 | 중 | 정정·재공고 빈도(기능 1이 먼저 필요) |
| 6 | 서류 의존 그래프(보조) | 제출서류 선후 관계로 준비 체크리스트 | 약 | 첨부 열람 가능 여부(이용 조건) |

**구성 제안(팀 결정 전).** 중심은 **1 + 5**, 사용자 가치로 **3**을 붙인다. 2와 4는 데이터를 확인하기 전에는 주장하지 않는다. 모든 기능은 SQL 베이스라인과 질문 유형별로 비교하고 지는 유형도 보고한다.

## 6. 선택지

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 사규 유지 | 현재 계획대로 | 일정 안정, 이미 구조 적재·설계·화면설계서 진행 | 온톨로지 필요성 약점 그대로(SQL 베이스라인 비교로 방어) |
| B. 공고로 전환 | 대안 초안을 기준으로 진행 | 갱신되는 데이터, 시연 쉬움, 강사 의견 부합 | 재작업(수집·정규화·라벨·설계서·화면), 근거 강도는 약~중으로 비슷 |
| C. 사규 유지 + 공고 아이디어 차용 | 입수 시점 검증, 자격 게이트 등만 가져옴 | 일정 위험 작음 | 주제 자체의 약점은 그대로 |

**재사용하는 것(B 선택 시):** 기술 스택, HWP5 변환·법령 수집 코드, 응답 정책·모델 교체·Plan B·KPI 틀, SQL 베이스라인 실험 설계.
**새로 하는 것:** 공고 수집 배치, 요건 온톨로지와 정답 라벨, 규칙 평가기, hwpx 파서, 화면, 평가셋, 설계서·온톨로지 설계서·화면설계서 재작성.

## 7. 제안

**지금 결정하지 말고, 짧은 검증 뒤에 정한다. 그동안은 사규를 유지한다.** 사전 확인으로는 전환의 장단이 갈려서, 근거가 부족한 채 일정을 바꾸는 위험이 더 크다고 본다(제 판단이며 팀이 달리 정할 수 있다).

검증할 것(결과가 약하면 A 또는 C):
1. 팀 인증키를 발급해 두 API를 **시험 호출**하고 실제 응답과 건수를 기록한다.
2. 창업 분야 공고를 **무작위 30건 이상** 골라 요건을 두 사람이 따로 정규화하고 일치도를 본다.
3. 그 결과로 근거 강도를 다시 평가한다. 이때 §5의 기능 1·5를 먼저 본다(법령·제도 정의에 의존하는 요건의 비율, 정정·재공고 빈도).

**팀이 정할 것:** ① 검증 기간과 결정 시한 ② 검증 담당 ③ 결정 기준(예: 실응답에서 요건이 서술 필드에만 있는 비율, 라벨 일치도, 법령 정의 연결이 필요한 공고 비율의 하한) — 기준값은 제안하지 않았고 팀이 정해야 한다.
