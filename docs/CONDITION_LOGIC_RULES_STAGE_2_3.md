# 2-3단계 논리 관계 후보 생성 규칙

## 목적과 입력

`tools/build_condition_logic.py`는 2-2단계 개선 산출물의 개발용 조건 후보만 공통 조건 스키마의 공고별 조건 집합으로 옮긴다. 입력은 `extracted/improved/development_conditions.jsonl`, `extraction_inputs.jsonl`, `representative_samples.jsonl`의 `DEVELOPMENT` 분할, 기존 30건 검수 대상 목록이다. 평가 분할과 나라장터 보류 공고는 읽어 처리하지 않는다.

## 조건 집합과 근거

- `ELIGIBILITY`, `EXCLUSION`, `PREFERENCE`는 각각 독립된 컬렉션에 둔다.
- 유형을 확정하지 못한 후보는 v1 스키마 예시와 같은 방식으로 자격 컬렉션 슬롯에 보존하되 `condition_type=UNCLASSIFIED`를 유지한다.
- 후보 객체, 조건 ID, 출처 참조, 원문 구간은 복사해 보존한다. 후보 ID를 새로 만들거나 조건 의미를 재해석하지 않는다.
- 후보가 없는 공고도 처리 상태를 출력한다. `NOT_EXTRACTED`와 `NO_RULE_MATCH_NOT_ABSENCE`를 사용하고 조건 없음으로 확정하지 않는다.

## 논리 관계 후보

- 복수 후보가 같은 조건 유형에 있을 때 그룹 후보를 만든다. `모두 충족`, `동시에`, `또는`, `중 하나` 등 명시적 연결 신호가 한 종류만 발견되면 해당 연산자를 `AND` 또는 `OR` 후보로 기록한다. 신호가 없거나 두 종류가 함께 있으면 `UNRESOLVED`로 둔다.
- 서로 다른 원문 필드의 조건은 연결하지 않는다. 단순히 후보가 목록에 함께 있다는 이유로 AND/OR를 추정하지 않는다.
- 근거를 계산할 수 있는 그룹은 원문 필드, 공고 ID, 시작·종료 오프셋 및 해당 원문 구간을 그룹 증거로 복사한다. 구간을 확인할 수 없는 그룹은 근거를 `null`로 두고 별도 관계 검수 목록에 남긴다.
- 모든 자동 그룹은 `NEEDS_REVIEW`이며 컬렉션 `logic_status=UNRESOLVED`, `decision_eligible=false`다. AND/OR 표시는 검수 후보이지 확정된 논리 관계가 아니다.
- 부정 표현만으로 `NOT`를 생성하지 않는다. 조건 자체 부정, 그룹 부정, 지원 범위 제외의 구분은 사람 검수가 필요하다. 기존 스키마와 중첩 구조 검증은 NOT를 포함한다.
- 예외·단서 감지 결과는 정확한 원문과 문자 위치를 `qualifier_candidates.jsonl` 및 사람 검수 자료에 보존한다. 적용 대상이 확인되지 않으므로 자동 연결하지 않는다.
- 같은 근거 구간에서 서로 다른 해석이 발견되면 모두 남기고 충돌 검수 대상으로 만든다. 현재 표본에서 이 기준의 충돌 묶음은 0개였다.

## 식별자와 검증

그룹·단서·충돌 ID는 정규 JSON 직렬화한 결정 입력의 SHA-256을 Base32로 인코딩해 만든다. 시간, 난수 또는 내장 `hash()`를 쓰지 않는다. `validate_graph()`는 공고 내 조건 참조 폐쇄성, 그룹 ID 중복, AND/OR/NOT 자식 수, 모든 후보 참조 여부와 판정 비허용 상태를 검사한다. 전체 공고 레코드는 기존 JSON Schema validator로 추가 검증한다.

## 제한

이 모듈은 논리 파서, 조건 판정기, 의미 정확도 평가기가 아니다. 사람 검수 전에는 출력의 논리적 타당성을 주장할 수 없다. 어휘 신호가 있어도 문장 범위와 예외, 조건 유형을 사람이 확인해야 한다.
